Static evidence (base DEX/native disassembly)
1. In classes7.dex, LX/CMk implements android.os.Handler$Callback. LX/Ahz.A00 constructs three
   CVC-backed LX/CMk handlers with discriminators 1, 2, and 3, storing discriminator 3 in CVC.A0G.
   On that handler's default branch, LX/CMk.handleMessage first casts its owner to LX/CVC and calls
   Llitex/settings/PrivacyActivity;->getPrivacyCalls(Ljava/lang/Object;)Z before processing the
   message. The following message-dispatch code includes the incoming-call key "participant_jid".
   If getPrivacyCalls returns true, the handler exits that path immediately.

2. In lib/arm64-v8a/liblitex.so, the exported native method
   Java_litex_settings_PrivacyActivity_getPrivacyCalls__Ljava_lang_Object_2 starts at VA 0x92558.
   It resolves CallInfo/peer-JID data, obtains the peer number, and builds per-number
   "walitex_block_calls_" preference names. It reads "walitex_block_calls_check" (string VA
   0x1cba8; xref at 0x92b80), the integer "walitex_block_calls_mode" (xref at 0x92c20), and the
   configured "walitex_blocked_country_prefixes" string (xref at 0x92d44). The function trims and
   iterates the configured values and contains a String.startsWith check (xref at 0x93694). Its
   matching/mode branch constructs litex/bridge/RunnableTask with integer discriminator 6
   (constructor setup around 0x931d4–0x93234), then obtains ScheduledThreadPoolExecutor.execute
   with the (Ljava/lang/Runnable;)V descriptor and submits that RunnableTask (around
   0x93250–0x932a8).

3. The RunnableTask native dispatcher has a mode-6 branch. Its runCase6 bridge starts at VA
   0x77594 and resolves com/whatsapp/calling/voipcalling/Voip->rejectCall with descriptor
   (Ljava/lang/String;Ljava/lang/String;I)V (method-name reference formed at 0x7774c). Thus there is
   a static route from the calls preference, through the call-message handler and RunnableTask, to
   WhatsApp's rejectCall API.

4. Candidate 264207411 does not replace WaResources.setBoolean; the original native preference
   writer remains. The reset-site patch changes only the verified false-argument store at 0x6ff60,
   preserving the earlier requested-value store at 0x6fe08. The banner suppression is isolated to
   Extra.setPrmBanner and does not itself establish that calls are rejected.

Interpretation and limits
- This is a concrete static enforcement path, not just a preference getter or UI marker. It makes
  it plausible that the calls feature will reject matching incoming calls when the saved preference
  and other mode/filter conditions permit.
- No incoming call has been tested with candidate 264207411 on an emulator or the S24 Ultra. Actual
  rejection, ring behavior, mode/filter semantics, and the caller-side result remain unverified.
- The candidate's switch persistence has not been emulator-tested. In-place installation of this
  exact candidate has not been tested; candidate 264207409 was separately verified with adb install
  -r over the exact base, but that is not a substitute for testing 411.
- Voice-note capture and Anti View Once repeat-view/download plus sender-visible “Opened” also remain
  unverified on the S24 Ultra.

Conclusion: useful local diagnostic candidate only. Do not label it unlocked, fixed, release-ready,
or verified on the user's phone until the above behavior is tested.
